# QuotaOps v0.2.0 resource measurements (Windows 11, 18 Nov 2026)

Tools: `scripts/windows-packaged-resource-profile.mjs` (per-role private
bytes, working set, CPU, handles) and `scripts/windows-packaged-render-check.mjs`
(rendering workload). Packaged `win-unpacked` builds, isolated temporary
home, disposable never-signed-in profiles, 32 logical CPUs. CPU % "of
machine" = all cores 100 %.

## Idle memory: what changed

| Build | Total private MB (median) | Working set MB | GPU process | Collector |
|---|---|---|---|---|
| 0.1.x (`83979a6`), GPU on, Playwright loaded at start | 318.9 | 454.8 | 98.7 | 97–115 |
| GPU off only | 241.6 | 433.7 | 21.3 | 97–115 |
| **0.2.0: GPU off + Playwright loaded on first launch (0 accounts)** | **212.3** | **399.0** | 21.3 | 71–75 |
| 0.2.0 with accounts, after first collection | 238–240 | 432–433 | 21 | 100 |

The collector keeps Playwright (~63 MB) once loaded: Node cannot unload an
ES module. Running each batch in a short-lived worker would return idle to
about 212 MB with accounts too; not done in 0.2.0 (design change: a second
process per batch and its own lifecycle tests).

## Collection cost

| Mode | Browser processes / private MB (peak seen) | CPU per account collection | Takes focus |
|---|---|---|---|
| 0.1.x headed "minimized/off-screen" | 11 / 787–902 | ≈ 6–7 CPU-seconds | **yes** (every collection) |
| 0.2.0 background (headless) | 7 / ≈ 242 | see 2 h run | **no** (0 of 67 foreground samples) |
| 0.2.0 visible (consented) | headed, as 0.1.x | ≈ 6–7 CPU-seconds | yes, after consent |

Scheduling: at the default 5-minute interval, five headed collections cost
about 35 CPU-seconds per 5 minutes, ≈ 12 % of one core averaged on a 4-core
PC, with 0.8–0.9 GB transient memory each time. Held accounts (challenge or
sign-in) are now skipped in the background, which removes the cost entirely
for them. Recommendation for the owner: 15-minute default interval
(÷3 cost), plus validation data on whether headless works at all.

## Long idle (0.2.0, one disposable account, window hidden to tray)

The account was challenged on its first, headless collection and then held
(no further browser launches), which is the expected state for a challenged
real account. Samples every 60 s; figures exclude the first 300 s.

| Checkpoint | Total private MB (min–max) | Working set MB | Collector | Renderer | Main | Handles | CPU % of machine (mean / max) |
|---|---|---|---|---|---|---|---|
| 30 min | 237.5–245.3 | 432–440 | 99.9–101.5 | 32.9–35.2 | 71.4–76.7 | 2475 → 2489 | 0.005 / 0.03 |
| 0.5–1 h | 244.5–251.6 | 440–449 | 99.6–101.5 | 35.2–36.9 | 75.6–81.1 | 2489 → 2497 | 0.009 / 0.05 |
| 1–1.5 h | 250.8–254.4 | 447–450 | 99.7–100.7 | 37.2–39.3 | 79.6–81.5 | 2499 → 2488 | 0.007 / 0.03 |
| 1.5–2 h | 253.6–257.3 | 450–453 | 99.7–101.0 | 39.3–41.3 | 80.2–82.4 | 2488 → 2486 | 0.001 / 0.01 |

Over two hours the total rose 238 → 256 MB. The collector was flat and
handles stayed level. The renderer grew linearly (≈ 4 MB/h). The main
process grew 71 → 82 MB, flattening after about 1 h. Both were doing work
nobody could see while the window was hidden:
- the dashboard polled every 30 s and replaced its state with equal new objects;
- main built a new native tray menu every 30 s.

`abab16f` removes both: the menu is rebuilt only when it changes, and the
hidden dashboard does not poll. The re-measurement is below.

| Same scenario, minutes 5–60 | Total MB | Growth MB/h (total / renderer / main) | CPU % mean |
|---|---|---|---|
| before `abab16f` | 237.5–251.6 | 14.4 / 4.0 / 10.4 | 0.006 |
| after `abab16f` | 238.7–248.0 | **7.9 / 2.2 / 6.2** | 0.000 |

Growth roughly halved. What remains slows down, consistent with heap
warm-up: in the 2-hour run the main process levelled off after about an
hour. A 24-hour soak with real accounts belongs in the owner's day-long
clean-machine test.

Peak in the whole run: first sample, during the single headless collection
(7 browser processes, 242 MB of the 500 MB total).
