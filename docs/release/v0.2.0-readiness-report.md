## 1. Focus stealing (owner P0) — fixed

Evidence before: the 0.1.x headed "minimized/off-screen" browser took the
foreground from the user's active app on every collection, dismissed open
tray menus and received keystrokes.

Anonymous comparison on claude.ai, 3 runs each, disposable profiles:

| Mode | Challenged by Cloudflare | Took the foreground |
|---|---|---|
| headless (0.2.0 background) | 3 / 3 | 0 / 3 |
| plain headed window | 0 / 3 (reached sign-in) | 2 / 3 |
| 0.1.x minimized/off-screen headed | challenged (2 / 2 earlier runs) | every run |

0.2.0:

- **Background collection is headless.** Scheduled collection runs headless on every platform, with no window, and the minimized/off-screen mode is removed.
- **Visible windows only with consent.** Tray → **Refresh with visible browser...** shows a dialog first, then runs that one batch in ordinary windows. The tray shows "Checking accounts now..." while it runs, and a notification at the end gives counts.
- **Background mode is configurable.** Set `backgroundCollection` to `"headless"` (default) or `"off"` (manual only).
- **Held accounts are not retried in a loop.** An account that is challenged or signed out is retried in the background at most once per 24 h. Holds persist across restarts and are shown in the tray at once.

Packaged E2E:
- `background-focus` PASS 2/2: 32–35 foreground samples, browser-owned 0, no headed browser.
- `visible-consent` PASS: Cancel opened nothing; after consent a visible browser ran; tray Quit during it took 0.26 s with nothing left running.

**Open question:** do signed-in accounts pass Cloudflare in headless mode? The anonymous evidence says probably not. Your validation kit answers it. If they don't, set `backgroundCollection: "off"` as the 0.2.0 default (one-line change). In that case 0.2.0 ships with the temporary manual mode you accepted as a fallback.

**Independent review before shipping.** An AI review of this change (not
the required human security review) found one high-severity defect, now
fixed (`c5a4375`). A refused or still-pending visible request survived
Pause, so a later Resume could open browser windows without consent. The
request type now travels with each queued refresh: visible beats manual
beats scheduled, Pause clears it, and a refused request remembers nothing.
The same commit fixes five smaller defects:

- hold changes are now saved when Quit or Pause stops a batch part-way;
- with background off, holds older than 24 h no longer vanish from the tray after a restart;
- two consent dialogs can no longer stack;
- the completion notice no longer counts an older snapshot;
- a failed state-file rename no longer leaves a temporary file behind.

Each fix has a regression test that fails on the old code where that
applies.

## 2. GPU acceleration — off by default on Windows (tested)

`app.disableHardwareAcceleration()` on Windows; set
`QUOTAOPS_HARDWARE_ACCELERATION=1` to turn hardware acceleration back on for
diagnosis. Workload: scroll, resize, minimize/restore, at scale 1 / 1.5 / 2.

| | Software (default) | GPU |
|---|---|---|
| Window ready | 182–266 ms | 308–312 ms |
| Private memory during workload | 218–249 MB | 316–363 MB |
| CPU during workload (% of one core) | 3.1–16.0 | 5.5–12.8 |
| UI latency p95 | 0.8–1.0 ms | 0.9 ms |
| Frames non-blank after scroll, resize and restore, at every scale | yes | yes |

Result: acceptable. About 100 MB less memory, a faster window and the same
responsiveness, at 2–4 points more of one core during heavy scroll or
resize. Not measured: animation frame rate. Measuring it would need a
debugging port, and the app deliberately has none. Full table:
`docs/performance/2026-11-18-v0.2.0-resources.md`.

## 3. Memory and CPU

Measured on the packaged app, by process role. Full tables:
`docs/performance/2026-11-18-v0.2.0-resources.md`.

| | 0.1.x | 0.2.0 |
|---|---|---|
| Idle private memory, 0 accounts | 319 MB | **212 MB** |
| Idle private memory, accounts, after first collection | 315–355 MB | 238–245 MB |
| Browser during one collection | 11 processes, 787–902 MB, takes focus | 7 processes, ≈ 242 MB, headless |
| Idle CPU | ≈ 0.01 % | ≈ 0.005 % |
| Leak check, 11 refresh cycles | no growth | no growth; held accounts launch nothing |
| 30 min idle | — | 237–245 MB, collector flat, +14 handles |
| 2 h idle | — | 238 → 256 MB, collector flat, CPU ≈ 0; growth in renderer and main halved by `abab16f` (14.4 → 7.9 MB/h in the first hour), levelling off |

Investigated:
- **Lazy loading** of `playwright-core`: shipped, −30 to −40 MB in the collector before the first collection.
- **Unloading:** Node cannot unload a module. Running each batch in a `worker_threads` worker does free it: about 50 MB after the worker exits, against 104 MB. That is about −50 MB more at idle with accounts. Deferred to 0.2.x, because it changes how collections run and needs its own lifecycle and orphan testing.
- **Scheduling:** each account collection costs about 6–7 CPU-seconds and the browser's memory. Recommended default interval: 15 min instead of 5 (a third of the cost). Your decision.
- **Renderer:** about 35 MB, about 0 CPU when hidden. Nothing worth changing.

On an ordinary 8 GB Windows PC this is about 240 MB at rest and about 500 MB during a headless check.

## 8. Proposed v0.2.0 distribution process

1. You review the stack (`docs/release/stacked-pr-review-guide.md`) and
   arrange the independent human security review.
2. You run the Claude validation kit. Its result decides the
   `backgroundCollection` default and the final wording of the release notes.
3. You choose the code-signing route: a cloud signing service, or an OV/EV
   certificate with an HSM-held key. Either way the key stays in a
   protected GitHub environment that requires a reviewer.
   `desktop/build-signed-candidate.mjs` is already proven in CI with a
   throwaway certificate: EXE and installer signed and timestamped, branded
   EXE icon, `SHA256SUMS.txt`.
4. A protected release job builds `v0.2.0-rc.1` from a tag and creates a
   **Draft** GitHub Release. It contains the installer, `SHA256SUMS.txt`,
   the release notes and the source ZIP (`git archive`).
5. Clean-machine checks on a disposable Windows 10/11:
   - fresh install;
   - 0.1.0 → 0.2.0 upgrade, with accounts, profiles and token kept;
   - uninstall keeps `%USERPROFILE%\.quotaops`;
   - SmartScreen and signature checks;
   - one day of normal use.
6. You approve, the release is published, and the 0.1.0 testers and
   repository users get their messages. Auto-update stays off; it is a later
   step with its own gate.
7. Problems after release are fixed with 0.2.1. Published assets are never
   replaced.
