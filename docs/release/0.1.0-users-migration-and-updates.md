# Plan: QuotaOps 0.1.0 users, communication and update delivery

Status: plan for the release owner. Nothing here has been sent or published.

## 1. Who has what

| Group | How they got QuotaOps | Can we reach their install? | Automatic updates? |
|---|---|---|---|
| A. Unsigned 0.1.0 installer users (Draft PR #39 build) | `.exe` shared directly | No. The build has no update channel (updater compiled in but disabled by policy) | **No** — never will |
| B. Repository users (git clone / ZIP) | Source | No | **No** — they pull or download new versions themselves |
| C. Future signed-installer users (0.2.0+) | GitHub Release | Only after a later, separately approved update channel | Not in 0.2.0 |

Nothing in any message may imply that groups A or B receive updates
automatically.

## 2. Communication

**Now (before 0.2.0 exists), to group A, through the channel they received the
build:**

> QuotaOps 0.1.0 has two known problems on Windows. Quit can appear to do
> nothing while accounts are being checked. Claude accounts can show
> "unsupported" when Claude asks for human verification. A corrected version
> is in testing. Until then: to close QuotaOps reliably, choose Quit while no
> check is running, wait a minute, and if a QuotaOps process remains, end it
> in Task Manager. Your accounts and settings are not affected.

**At 0.2.0 release:** the release notes (`v0.2.0-release-notes-draft.md`)
plus a short message to group A with the download link, checksum and
signature check, and "install over 0.1.0; your settings are kept".

**Group B:** a pinned issue and README section listing the tag (`v0.2.0`),
the upgrade steps and the same known limitations.

## 3. Installing 0.2.0 over 0.1.0 (to verify before release)

- Same NSIS per-user installation path and app id: installing 0.2.0 replaces
  0.1.0 in place. To be proven in the clean-machine test: install 0.1.0 →
  add disposable accounts → install 0.2.0 → accounts, profiles, token and
  settings intact → uninstall keeps `%USERPROFILE%\.quotaops`.
- 0.1.0 must be quit first; the installer must detect a running QuotaOps and
  ask the user to quit it (to verify; add if missing).
- New file `collector-state.json` (statuses and timestamps only) is created
  on first run; no migration of existing files.

## 4. Secure update workflow for future signed versions

Order of work. Each step needs the owner's approval; none is active in 0.2.0.

1. **Signed builds only.** A protected GitHub Actions release job (manual
   dispatch, protected environment with required reviewer) builds from a tag,
   signs `QuotaOps.exe`, the uninstaller and the installer with the
   organisation's Authenticode certificate (cloud signing or HSM-backed key;
   never a password or key in the repository), and produces `SHA256SUMS.txt`.
2. **Publishing.** The job creates a **Draft** GitHub Release. A person checks
   the signature and checksums on a clean machine before publishing. Published
   assets are never replaced; problems are fixed with a new version.
3. **Update channel (later release).** Enable the existing, disabled
   `electron-updater` path only after a signed old → new upgrade has been
   tested, including declined and cancelled updates, offline use, corrupt or
   tampered metadata, a publisher mismatch, and collector shutdown during
   install. The updater accepts only the pinned publisher name; the user
   confirms every download and every install.
4. **Rollback.** Keep the previous signed installer on its release page; a
   bad release is fixed by a newer version, never by changing a published file.
